O1 — contract and source feasibility: AcceptWithScope

The represented OwnsNode, advisor node/facts/input/origin checks, and snapshot-specific typed-container issuance/read shapes can express Schema’s required authentication through this concrete provider-local design:
- Each admitted immutable graph belongs to a private input owner. Sealed node projections retain that exact owner and their registered underlying node identity.
- Membership checks input availability, the trusted projection type, exact owner reference and admitted-node association before invoking content getters.
- Every node-producing route preserves the association, including parent, document, axes, attributes and namespace projections.
- Trusted copy operations register a distinct snapshot and its node-to-original-fact associations. Preserve copies retain original assessment/component facts; strip copies expose no assessment authority. Labels, equal digests and copied carrier references do not authenticate membership.
- Typed containers are privately issued and registered against the precise input, node, facts and origin. Authentication precedes enumeration or value access; reads validate each atomic value’s actual type and provenance.
This is a feasible design direction accepted for implementation. The legacy public assessment carrier remains a trusted-host annotation mechanism and is insufficient for BCAP authentication.

No additional Core member is demonstrated as necessary by the supplied map. Actual adapter correctness remains unproved.

O2 — finite policy and represented requirements: AcceptWithScope

Schema accepts:
- Required caller-supplied positive finite snapshot/cache/atom/digit limits and nonnegative scale.
- An invalid default SchemaQueryLimits value, with explicit validation.
- Explicit exact-decimal coefficient-digit and scale capacity before normalization, plus explicit formatting output capacity.
- No implicit workload defaults or unlimited fallback.
Selecting workload ceilings is R4 work; it is not an unresolved R2 policy decision.

The accepted design retains list shape, per-atomic actual type/provenance, union-member distinctions, nil and no-typed-value as separate concepts. The native decimal-leaf/element-only-root evidence does not qualify general list, union, nil or full XSD 1.1 behavior.

Known N1–N8 requirements remain mapped to authority/advisor/context/episode/lifetime shapes. Unsupported operations must report Unsupported, rather than false or empty success.

Compatibility remains directional across source, target and environment, with explicit Compatible, Incompatible and Unsupported outcomes. Copying, matching QNames, equal digests or shared labels do not constitute compatibility proof.
