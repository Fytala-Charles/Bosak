1b9cb58279d71c041907387a41102375f2ac1bff:docs/AGENT_HANDOVER.md:5:**Current focus:** **REQ-118 slice 4.0-S6a landed: the XPath 4.0 type-system first piece behind the 4.0-S0 gate — enumeration types and choice item types — with no XDM changes.** Semantics verified against the live XPath 4.0 WG Review Draft (qt4cg.org, spec text extracted this session). **Key architectural fact:** the type system is entirely string-based — `CastNode`/`InstanceOfNode`/`TreatNode` carry a `string TypeName`, and `VmEngine.ValueMatchesType`/`TryCast`/`ApplyFunctionConversion` are the single matchers — so enum/choice are new type-text branches, not new XDM types. **Enumeration types (§3.2.6):** `enum("red","green")` in any ItemType position (instance-of, cast/castable target, function param/return). An enum is a *structural* type over xs:string: members compare with codepoint (ordinal) equality, instances are **not** re-annotated (a matching value stays a plain xs:string — `XdmValue.FromString`), a multi-member enum ≡ the union of its singletons, and `xs:untypedAtomic` is **not** an instance (not an xs:string subtype — the engine stores untypedAtomic as String-kind, so the enum branch in `ValueMatchesType` excludes it via `IsUntypedAtomicValue`) although it *casts* to the enum (§3.4.2 rule 05: untypedAtomic/anyURI → xs:string first). A non-member cast is a lexical failure → FORG0001; `enum()` (empty member list) is XPST0003. **Choice item types (§3.2.5):** `(xs:date|xs:dateTime)` — a value matches when any alternative matches; choices may mix node-kind and atomic types (`(map(*)|array(*))`, `(element(a)|xs:string)`); an all-atomic choice is a generalized atomic type and a valid cast target (`cast @when as (xs:date|xs:dateTime)`). **In-order alternative semantics (§3.4.2 rule 02 / F&O §23.3.7) — the subtle part:** casts and function coercion try alternatives *in declaration order*, interleaving per alternative: if the value matches the alternative → returned unchanged; else try casting to the alternative; first success wins. The spec's own fn:char example pins this: an integer against `(xs:string|xs:positiveInteger)` arrives as the **string**. The engine's existing any-match fast paths (`ApplyFunctionConversion`'s whole-value pass-through and `ConvertAtomizedItem`'s first check) had to be gated off for choice targets — they would return the integer unchanged. All alternatives failing → FORG0001 for `cast as`, XPTY0004 for function-argument mismatch. Node arguments against all-node-kind choices (`(element(a)|element(b))`) pass through unchanged via `IsNodeKindTestType` recursing into choices (`All` semantics); mixed node+atomic choices atomize (documented deviation: the spec would pass the node through when a node-kind alternative matches, Bosak atomizes — value-equal results).
