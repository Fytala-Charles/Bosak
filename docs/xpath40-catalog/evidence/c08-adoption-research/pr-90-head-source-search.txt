Consequences: all map operations (`map:get`, `map:merge`, serialization, providers) work unchanged on records, **plain maps never match any record type** (`map{"x":3} instance of record(x)` → false, per qt4tests RecordType-001a), and the lookup-operator field check is annotation-presence-gated so 3.1 behavior is bit-identical. **Type syntax (§3.2.10):** `record(*)` (any annotated record), `record()` (empty record), `record(field as SequenceType?, …)` — field names are NCNames or string literals, omitted field type ≡ `item()*`, duplicate field names XPST0021, trailing comma allowed by the grammar; NO extensibility marker (dropped from the draft). The parser captures the type text verbatim in `ParseTypeNameAndParens` (same mechanism as S6a `enum(`) and the field list is re-parsed by a shared quote/paren-aware `TryParseRecordTypeFields` (internals-visible to the runtime, like `TryParseEnumTypeMembers`). **Instance-of** is structural with exact entry count == field count; per-field recursive `ValueMatchesType` gives the spec's covariant field subtyping for free (`record(a as xs:integer)` matches `record(a as xs:decimal)`). **Coercion (§3.4.2 rule 10)** — `function($r as record(a as xs:integer)) {…}` called with a plain map: builds a NEW annotated map in field-declaration order; missing fields become `()` entries (XPTY0004 when the field type requires a value); **surplus keys XPTY0004**; present values coerced recursively via `ApplyFunctionConversion` (numeric promotion applies). **Cast (§4.19.2.7)** differs deliberately: present values are *kept* when matching else **cast** to the field type (value-cast failure → FORG0001); **surplus keys are DISCARDED**; `record(*)` is an assertion (XPTY0004 on a plain map, empty→empty for `?`). Spec example pins it: `{"first":"John","middle":"Ignatius","last":"Smith"} cast as record(title, first, last)` → `{"title": (), "first": "John", "last": "Smith"}`. The Cast/Castable VM opcodes skip `AtomizeForCast` for record targets (maps would otherwise hit FOTY0013) and `TryCastToRecord` runs before TryCast's own atomization. **Lookup (§4.15.3):** `?key` and record-as-function calls raise XPTY0004 for keys that are not declared fields (per key in the multi-key `?(…)` form, via `LookupInto`→`LookupSingle`); `?*` is unaffected; the `map:*` functions stay field-blind per spec. **`but with` (§4.15.4):** `ButWithExpr` sits directly under `IntersectExceptExpr` (left-assoc; `but`/`with` are contextual Name tokens); `$A but with $B` ≡ `let $temp as R := map:merge(($A,$B), {'duplicates':'use-last'}) return $temp` where R is A's annotation — implemented as `VmEngine.ButWith`: LHS must be an annotated record (plain map → XPTY0004, there is no annotation to name R), RHS must be a map, merge use-last via `WithAdded`, then re-coerce through `CoerceMapToRecord` (unknown fields and bad value types → XPTY0004; result keeps the annotation, so chaining works). **No new AST node:** `BinaryOperator.ButWith` on `BinaryExpressionNode` — every traversal consumer (optimizer, static validator, Api resolution, XSLT/XQuery analyzers) already handles binary nodes generically; only a new `IrOpCode.ButWith` (IrOpCode 1.9, inserted after `Pipeline` — enum shift is compile-time only) + lowerer mapping (IrLowerer 1.50) + VM case were needed.
310ab3a50c8457cecf0a24fded8da3007ed4cac1:docs/AGENT_HANDOVER.md:17:**Current focus:** **REQ-118 slice 4.0-S6a landed: the XPath 4.0 type-system first piece behind the 4.0-S0 gate — enumeration types and choice item types — with no XDM changes.** Semantics verified against the live XPath 4.0 WG Review Draft (qt4cg.org, spec text extracted this session). **Key architectural fact:** the type system is entirely string-based — `CastNode`/`InstanceOfNode`/`TreatNode` carry a `string TypeName`, and `VmEngine.ValueMatchesType`/`TryCast`/`ApplyFunctionConversion` are the single matchers — so enum/choice are new type-text branches, not new XDM types. **Enumeration types (§3.2.6):** `enum("red","green")` in any ItemType position (instance-of, cast/castable target, function param/return). An enum is a *structural* type over xs:string: members compare with codepoint (ordinal) equality, instances are **not** re-annotated (a matching value stays a plain xs:string — `XdmValue.FromString`), a multi-member enum ≡ the union of its singletons, and `xs:untypedAtomic` is **not** an instance (not an xs:string subtype — the engine stores untypedAtomic as String-kind, so the enum branch in `ValueMatchesType` excludes it via `IsUntypedAtomicValue`) although it *casts* to the enum (§3.4.2 rule 05: untypedAtomic/anyURI → xs:string first). A non-member cast is a lexical failure → FORG0001; `enum()` (empty member list) is XPST0003. **Choice item types (§3.2.5):** `(xs:date|xs:dateTime)` — a value matches when any alternative matches; choices may mix node-kind and atomic types (`(map(*)|array(*))`, `(element(a)|xs:string)`); an all-atomic choice is a generalized atomic type and a valid cast target (`cast @when as (xs:date|xs:dateTime)`). **In-order alternative semantics (§3.4.2 rule 02 / F&O §23.3.7) — the subtle part:** casts and function coercion try alternatives *in declaration order*, interleaving per alternative: if the value matches the alternative → returned unchanged; else try casting to the alternative; first success wins. The spec's own fn:char example pins this: an integer against `(xs:string|xs:positiveInteger)` arrives as the **string**. The engine's existing any-match fast paths (`ApplyFunctionConversion`'s whole-value pass-through and `ConvertAtomizedItem`'s first check) had to be gated off for choice targets — they would return the integer unchanged. All alternatives failing → FORG0001 for `cast as`, XPTY0004 for function-argument mismatch. Node arguments against all-node-kind choices (`(element(a)|element(b))`) pass through unchanged via `IsNodeKindTestType` recursing into choices (`All` semantics); mixed node+atomic choices atomize (documented deviation: the spec would pass the node through when a node-kind alternative matches, Bosak atomizes — value-equal results).
