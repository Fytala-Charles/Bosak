## 3. Trace: Schema Compilation and Validation Today

### 3.1 Entry point (this repo)

`src/Bosak.Schema/SchemaAwareXslt.cs` is the **only** schema-aware surface the add-on exposes:

- `CreateCompiler()` → `new XsltCompiler { SchemaAware = true }`
- `CreateCompiler(string schemaDirectory)` → additionally sets a file-system `SchemaResolver` delegate (`Func<string baseUri, IReadOnlyList<string> hints, Stream?>`); unresolved hints fall back to core default URI resolution.
- Both are gated by `EnsureActivated()` — check-at-gate re-evaluation of `License.Current.IsUsable` (REQ-002/004). An unactivated or expired-beyond-grace package throws `InvalidOperationException`, bit-identical to the free core.

No other file in `src/Bosak.Schema/` touches schema machinery (`License*.cs`, `LicenseTier.cs`, `ActivatedLicense.cs`, `LicenseValidationException.cs` are licensing only).

|--------|------------------------|
| `SchemaAware` | `bool` — opt-in gate; without it `xsl:import-schema` raises XTSE1650 |

### 3.5 Test usage pattern (tests/Bosak.Schema.Tests)

`ImportSchemaSliceTests` and `ComplexTypeValidationTests` exercise: `License.Activate(TestKeys...)` → `SchemaAwareXslt.CreateCompiler(schemaDir)` → stylesheet with `xsl:import-schema` + `schema-location` hint → `Compile` → source as `XDocumentNode` → `TransformToString`. Validation-on-construction via `xsl:copy-of validation='strict'` and literal result elements with `@type`; error surfaces verified: XTSE1650 (inert), XPDY0050, XTTE1540, XTTE1510, FOTY0012. `InertBeforeActivationTests` pins the unactivated boundary (`InvalidOperationException`, plain-compiler XTSE1650).

### 3.5 New in the 1.26.3 line (repoint findings, 2026-10-27)

Reflection dump of the 1.26.3 assemblies: the §3.2–3.4 schema surface is present unchanged in kind, plus two additions relevant to REQ-009:

- **`Bosak.XPath.Runtime.Resources.ControlledSchemaResolver : XmlResolver`** — constructed from a **`ControlledResourcePolicy`** (authority via `IControlledResourceAuthority`, supported `ControlledResourceRoute`s, `Receipts` audit trail, `RefusedCode`/`UnsupportedCode`, credential redaction). This is a policy-based resource-resolution framework in the core — **S1's "secure schema resolution" requirement (default deny, allowlists, bounded behavior) should build on this rather than invent a parallel mechanism**, pending an S1 design check of its defaults.
- **`Bosak.Xslt.Validation.XsltValidation` family** (`XsltValidation`, `XsltValidationOptions/Result/Outcome/Coverage/CoverageGap/Diagnostic`) — an *authoring-time* stylesheet validation API over `AuthoringSnapshot`/`AuthoringSource`, with an explicit `UnsupportedCoverage`/`Refused` outcome model and declared coverage slots (expression/pattern/AVT/static-variable/structural). Not XSD document validation, but its **explicit "refused / unsupported coverage" diagnostic posture is the pattern REQ-009 should mirror** for unsupported XSD 1.1 constructs.

## 4. Critical Finding — the Seam Is `XmlSchemaSet`-Typed

**Every schema-bearing API in the seam — on 0.12.1-beta *and* re-verified on 1.26.3 — `XsltCompiler.SchemaSet`, `EvaluationContext.SchemaSet`/`GetSchema*`, `XdmSchemaAnnotator.*`, `IXsdValidator` inputs — is typed against `System.Xml.Schema.XmlSchemaSet` and its component model.** .NET's `System.Xml.Schema` implements **XSD 1.0 only**; it cannot represent XSD 1.1 constructs (`xs:assert`, `xs:alternative`, `xs:assertion`, open content, `xs:override`, …), and its validator cannot evaluate them.

Consequences for REQ-009:

1. **The handover's premise is confirmed** — XSD 1.1 needs a new immutable compiled schema model *inside* `Bosak.Schema` (S1); there is no 1.1-capable component model to reuse from the platform.
2. **The current seam cannot carry XSD 1.1 components.** `xs:assert` etc. compiled in the add-on cannot flow into the engine through `XmlSchemaSet`-typed members. The engine's *validation behavior* for 1.1 documents must therefore be driven either by (a) pre-validating/annotating via a new add-side pipeline and mapping results onto existing PSVI annotation mechanisms, or (b) new core seam abstractions — a **public Bosak API change**, which per REQ-009's acceptance criteria and the handover's non-negotiable boundaries requires a separate compatibility ADR and explicit approval *before* S1/S2 design is frozen.
3. **Assertion XPath evaluation** is feasible through the existing public `RegisterFunction` / compiled-expression surface, but the W3C-constrained static context (no free variables except `$value` context semantics, restricted function library, typed-value access) needs the compatibility layer the handover warns about — no engine change required for evaluation itself, only for *where* assertions hook into validation.
4. **PSVI lifetime:** `XdmSchemaAnnotator.Annotate(XObject, IXmlSchemaInfo)` shows the engine's annotation side table is `IXmlSchemaInfo`-based (XSD 1.0 shapes). A 1.1 annotated view needs an explicit strategy (immutable annotated view vs snapshot-scoped side table) as flagged in the handover.
