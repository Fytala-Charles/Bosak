## Proposed answers to Schema’s four questions

| Question | Core proposal | Consequence / evidence required |
|---|---|---|
| Neutral identity handles (N1/N8) | Use opaque provider-issued component handles scoped to an issuing authority and schema universe. Keep session, schema/instance source and snapshot identities distinct. | Derivation, affiliation and closure (N2) | Treat these as authority-backed query capabilities, not caller-asserted advisory metadata. Distinguish unsupported capability, an absent component and a supported negative relation. | Select exact operations only after mapping lookup, element affiliation and reachable-component traversal use cases. | Session/advisor lifetime (N4/N7) | Use an explicit opt-in compiled semantic environment retaining the selected provider/session and immutable profile. Obtain assertion/alternative assessment facts from Schema authority; do not move its validator into Core. Keep source trees/snapshots caller-owned. | Separate shareable compiled assessor safety from snapshot mutation, revocation and concurrent disposal. Provider cancellation must throw without successful partial output; do not copy the prototype Cancelled outcome into production by default. Capturing references alone is not semantic-capture or lease proof. |
| List/union timing (N3) | Specify the full required transport semantics before joint freeze, including sequence/list boundaries, actual union member type and original provenance. A bounded implementation may explicitly refuse unsupported cases while the backend develops. | Do not freeze a decimal-only carrier and defer a known required representation incompatibility. These are proposed design resolutions, not an accepted signature manifest or new normative adoption. The 32-type prototype is evidence, not the implementation specification. In particular, new affiliation/closure operations, opaque issuance and general atomic transport must be resolved rather than inferred from generated record members or the decimal bridge.
