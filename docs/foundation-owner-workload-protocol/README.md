# Owner workload measurement proposal — TA-51

A reproducible **candidate-only PF-03 subset protocol** now records one-child and eight-child decimal workloads within the existing provider capacity. It uses three independent provider sessions per fixture, two warmups and five measured cycles per session: **30 measured cycles and 135 checked decimal reads**. The Release build has zero warnings/errors. No provider or Core source was changed.

[Protocol](PROTOCOL.json) pins schema/instance bytes, query, semantic profile, finite limits and the whole-cycle measurement unit. [The runner](workload/Program.cs) references the exact frozen immutable-provider DLL and nine qualified engine DLLs; it never rebuilds the provider. Each cycle parses, assesses, admits, projects, evaluates all selected children in one raw operation and disposes owners. Compilation is separately recorded outside the execution window. Raw samples, allocation per cycle/cell, GC and retained-memory/weak-root observations remain available.

[Measured summaries](evidence/SUMMARY.json) show repetition medians about **80–107 ms for one child** and **686–757 ms for eight children**. Allocation is about **150 KB** and **204–208 KB per cycle**, respectively. All measured sums/counts agree and no measured output roots were observed alive after forced GC. These small samples do not establish tail-latency SLAs, statistical regression significance, zero retention or owner acceptance. Residual public-data CPU cost remains a separate attribution task; the prior serialization allocation correction stays intact.

[Method comparison](tools/compare.py) passes **14 synthetic controls** and refuses wrong fixtures/profile/limits/scope, environment drift, stale protocol hashes, missing/duplicate repetitions, invalid samples/allocation values and acceptance claims. Its baseline mode correctly refuses the actual candidate receipt presented as a baseline. Explicit repeatability mode never grants owner acceptance. The checker validates measurement methods only; separate cohort/load qualification and owner receipts are still mandatory.

[Baseline eligibility](BASELINE-ELIGIBILITY.json) leaves the baseline unset. Earlier TA-49/50 pilots used different schema bytes and measurement drivers and cannot supply a regression ratio for this protocol. A repository-recorded shipped release is not eligible merely because it has a version number: matching public capabilities, fixtures/profile, binary/configuration pins and loaded bindings must first be established. Candidate repetitions cannot fill the baseline slot.

[Budget proposal](BUDGET-PROPOSAL.json) keeps **all nine PF scenario budgets and acceptance slots unfilled**, with explicit suggested units and no invented thresholds. The two fixtures are a proposed native-decimal subset, not actual XmlDb/Braid workloads or broad list/union/construction/persistent/concurrent coverage. Owner workload selection and review remain required.
