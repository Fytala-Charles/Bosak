| Affected section / source anchor | Review consequence |
|---|---|
| §3.1 Basic Concepts; §4.2 Type System | Schema types and item types differ. Records, functions, choices and JNodes must not become XSD-provider components merely because both systems discuss types. |
| §4.1.1 `xsd-versions` | XDM's atomic semantics use XSD 1.1 definitions, while schema validation may use an XSD 1.0 processor. Full XSD 1.1 validation in Apache core is not a prerequisite for XDM 4.0. Explicit backwards compatibility and range limits need documentation. |
| §4.1.4 Schema Consistency | Compatibility concerns the union of schema components, including transitive definitions. Independent compatible schemas can have different validation outcomes because their universes contain different declarations/types. Original PSVI must survive interchange; revalidation is not an equivalence test. |
| §4.1.5 `types-representation` | Expanded QNames name schema types, but do not prove compatibility of two authorities. Anonymous types require sufficient derivation information and host-defined scope. Opaque identity is useful implementation machinery, not a replacement for those semantics. |
| §4.1.6 `xml-and-xsd-versions`; §5.2 String Values | XML 1.1 character acceptance differs from XML parser/serializer capabilities; optional NUL/noncharacters are separate from mandatory ranges. Unpaired surrogates are forbidden. An arbitrary CLR string constructor is not a complete character-validation boundary. |
| §5.7 Comparing Atomic Items | Type families and exact numeric magnitude connect `atomic-equal`, `compare`, map keys and comparison operators. General duration ordering is defined. Independent old paths must be reconciled by profile. |
| §6 `generic-nodes`, `node-identity`, `document-order` | GNodes collectively cover XML nodes and JNodes; identity and stable total document order are required. This abstract model does not mandate one CLR interface or new XML node-kind values. |
| §7.4.3 PSVI mapping; §7.6.13–14 type/typed-value; §7.6.17 location | Preserve declaration/type, nilled state, absent typed value and atomization. Location can be absent; it does not force a new mandatory persisted XML field. |
| §8.2 Map Items; `dm-map-put`, `dm-iterate-map` | Entry order is observable in traversal and JSON serialization. Replacing an existing key retains position; adding an absent key appends. Historical tombstones do not make a removed key present. |
| §8.3 Records | Simple record types match ordinary maps structurally; labeled records carry a label, forbid extra fields and use declaration order. A record label is distinct from a schema annotation and a schema session token. |
| §8.5 `id-JNodes`; §9 Conformance | JNodes have tree context and identity; navigation alone does not qualify the whole model. A root represents a map/array. |

## Source-backed capability matrix

These observations use current C42-identical binaries and **do not describe the older consumer binaries as tested**. Probe IDs resolve to exact expressions and both profile results in [observations.json](evidence/observations.json).

| Area | Actual support / observation | Gap or qualification required |
|---|---|---|
| XML nodes | `IXdmNode` exposes seven XML kinds, identity, order, lazy axes, default schema accessors and serialization. | Retain this implementer contract. Providers still need differential identity/order/atomization tests; a generalized node abstraction can be internal or additive. |
| JNodes | Separate `XdmValueKind.JNode` / `XdmJNode`; key/value/parent navigation probes succeed in 4.0. 3.1 refuses 4.0 functions. | `jnode-root-identity`, child identity and order all raise XPTY0004. `EvaluateNodeComparison` admits only `IsNode`; `JChildren` makes fresh wrappers. A tree/position identity and stable ordering design is required; wrapper reference equality alone will not suffice. `jtree(1)` also returns a JNode rather than refusing the non-map/array root. |
| Numeric comparison | `numeric-atomic-equal` is false, generalized `numeric-compare` is 1, map size is 2 for double 1.1 / decimal 1.1. | `numeric-eq` is true in both profiles. The 4.0 operator disagrees with the pinned exact-magnitude model; 3.1 behavior must be retained deliberately. |
| Durations | 4.0 generalized `duration-compare` returns 1 for P1M / P1000D, consistent with months-first ordering. | `duration-order` raises XPTY0004 in both profiles. Existing plain-duration rejection remains an old-profile guard; new-profile operators need a separately adopted change. |
| Binary equality | 4.0 `binary-atomic-equal` returns true for hexBinary 01 / base64Binary AQ==. | `binary-map-keys` returns size 2. The map-key comparer lacks the binary equality/hash path used by the function. Investigate affected profiles and published behavior separately before changing the shared comparer. |
| Map order | Replacement yields `a,b`; JSON serializes `b,a` in insertion order. `XdmMap` tracks explicit order. | Removal followed by insertion yields `a,b`, where the pinned constructor rule requires `b,a`; tombstone slot reuse appears in `Add`/`WithAdded`. The immutable-dictionary constructor starts in hash enumeration order. No global stable-order certification follows from two passing examples. |
| Records | `XdmMap.RecordType`, field descriptors, casts and named-record reference matching exist. | Plain map `instance of record(a as xs:integer)` is false, including with an extra field; pinned simple matching requires true. Existing tests intentionally expect the older annotation-based behavior. `XdmRecordType.Any`, textual types, label scope and map-update preservation need reconciliation rather than reuse as schema-component identities. |
| Atomic annotations | `XdmValue` stores built-in/user type names and inline/reference payloads; C44 proposes an envelope in the existing reference slot. | Equal type names do not establish shared component definitions. Preserve compatibility-aware actual type and anonymous derivation across atomization/copy/casts; audit every accessor, equality/hash and serializer. The 48-byte carrier result is inherited experimental evidence, not real-consumer ABI acceptance. |
| XML characters | Codepoint 1 round-trips in both profiles; codepoint surrogate 55296 refuses with FOCH0001; NUL also refuses. | NUL refusal is an allowed policy, not a defect. One scalar control is not an exhaustive Unicode/parser/serializer audit. Public CLR string factories and all serialization methods still need explicit boundaries and malformed UTF-16 checks. |
| Calendar range | Year-zero and year-10000 date construction stringify correctly in both profiles; +INF constructs. | `year-from-date` over those dates raises FODT0001 through bounded conversion. Construction does not establish complete extended-year operations. This preserves the documented limitation. |
| Serialization | `XdmJsonSerializer`, `XdmSerializer`, XML provider and XSLT output paths exist. Ordered JSON example succeeds. | Outputs are observable consumer behavior. Check each method's character/type/error handling and annotation unwrapping; do not serialize process-local session/issuer objects. No full Serialization 4.0 review is claimed. |

An additional cross-document total-order control over two parsed in-memory XML documents returns true in both profiles. It does not certify persistent nodes across snapshots, provider mixtures, every comparison direction or mixed XML/JNode order. No such success is inferred for XmlDb.

## Deliberate review exclusions and proposed restrictions

No intentional **new adopted deviation** is introduced. Current mismatches remain recorded diagnostics. The frozen 3.1 gate and currently adopted 4.0 profile stay unchanged; a later fix must name its adoption sections and test old/new profiles explicitly.

C44's same-session-only interoperability is a proposed restriction requiring revision or an explicitly bounded capability statement. It must not be described as full §4.1.4 support. Likewise a provider may explicitly refuse unimplemented XSD 1.1 coverage, but must not return a partial component closure or successful downgraded assessment. License checks remain in Bosak.Schema. Persistent arbitrary XDM values, complete current-draft certification, storage migration and new public interfaces remain unapproved scope.
