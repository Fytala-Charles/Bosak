# Native compatibility lane procedure

LANE-INPUTS.json freezes the original native output layout, source/fixture hashes and the exact nine-engine 1.81.0 candidate. The native source head is recorded before work; original inputs and tracked worktree status are checked again after execution. Only generated files under .guard-tmp/native-schema-181-lane are written. No native production file or prior layout is edited.

The baseline is a fresh frozen copy of the native 451-case test layout. Its deps metadata declares 1.34.2 project dependencies, which is distinct from older documentation describing 1.34.1. The fresh 451/0 baseline control establishes the exercised bytes; no historical identity is silently rewritten. The old 114-test dossier/layout is a different historical scope and is left untouched.

The source lane uses explicit read-only native .cs inputs in isolated SDK source/test wrappers, with the original assembly names and fixed references to nine DLLs extracted from the qualified 1.81.0 engine archive. It does not rebuild Core or overwrite native bin/obj. The wrapper's diagnostic SDK metadata is not a Schema package version or package qualification. The source build must pass before tests run. Initial restore could not reach the vulnerability feed and failed NU1900; a fresh command-scoped NuGetAudit=false retry used cached versions and passed with zero warnings/errors. That diagnostic setting grants no production vulnerability clearance.

The binary lane copies the entire baseline layout and replaces exactly the nine allowlisted engine DLLs. The test DLL, Schema DLL, host/deps/runtimeconfig, third-party assemblies and fixtures are not rebuilt or modified. A passing baseline precedes replacement execution. Each lane runs the compiled test assembly through the scoped watchdog with a 300-second limit and the existing startup observer. Negative cases remain caught by xUnit; no deliberately unhandled .NET diagnostic or machine-wide error-reporting change is used.

The dedicated tools/run-retained-foundation-caller.py remains required for its separate LegacyCaller.dll contract. FOUNDATION-CANDIDATE.json prepares the exact current seven-assembly subset for that runner, but LegacyCaller was not executed in this step. The native Schema xUnit lane instead has nine engines and 451 cases; it is not mislabeled as the 20-case foundation caller.

After execution, reconcile exact case names/outcomes, all loaded engine hashes/default contexts, full execution-layout hashes and the engine-only binary delta. Archives retain layouts, raw TRX/log receipts and wrapper bytes. Do not sum the three 451-case scopes or infer full native/public-provider coverage from backward compatibility. Current Core 26,338-unit/frozen-gate qualification is retained unchanged rather than freshly rerun. Package metadata is reevaluated without packages or publication.
